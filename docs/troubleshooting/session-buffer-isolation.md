# 측정 간 센서 이력 혼합 재현과 세션별 버퍼 분리

작업일: 2026-10-15(한국 시간) · 대상: Python 추론 코어 · 상태: 로컬 구현·검증 완료, 미커밋·미배포

후속 기록(2026-10-27): [모델 준비·입력 오류 처리](model-readiness-and-input-validation.md)를 추가했다. 아래 검증 수치와 남은 작업은 세션 분리 당시 기록이다.

## 문제와 재현

기존 `services/model_service.py`의 전역 `BUFFERS`에 모든 요청의 자기장 값이 들어갔다.
동시 실행이 아니어도 A·B의 샘플을 번갈아 처리하면 최근 16개에 서로 다른 측정이 섞였다.
이는 합성 입력으로 확인한 구조적 결함이며 운영 장애나 실제 위치 정확도 측정 기록은 아니다.

고정 사례 `smooth_variation`(A)과 `step_changes`(B)의 각 48개 샘플을 단독 실행한 결과와
A1 → B1 → A2 → B2 순서로 공유 버퍼에 넣은 결과를 비교했다.

| 단독 실행과 달랐던 항목 | A / 48개 | B / 48개 | 합계 / 96개 |
|---|---:|---:|---:|
| 기존 공유 버퍼의 위치 코드 | 11 | 14 | 25 |
| 기존 공유 버퍼의 후보 목록(코드·순서·점수) | 43 | 44 | 87 |
| 세션 분리 후 위치 코드 | 0 | 0 | 0 |
| 세션 분리 후 후보 목록 | 0 | 0 | 0 |

기존 후보 차이는 목록의 직접 비교로 집계했다. 수정 후 결과 비교는 기존 회귀 기준과 동일하게
코드·순서를 엄격히 검사하고 점수에만 상대 오차 `1e-9`, 절대 오차 `1e-12`를 허용한다.
공유 세션을 사용하는 기존 HTTP 호환 경로에서는 위 문제가 여전히 재현된다.

## 해결 방법과 선택 이유

- [PredictionSession](../../services/prediction_session.py)이 측정 하나의 최근 16개 이력과 종료 상태를 소유한다. 모델·스케일러는 기존처럼 공유한다.
- [run_prediction](../../services/model_service.py)은 세션을 필수 인자로 받는다. 보정 → 버퍼 갱신 → 웨이브렛 → 스케일링 → 추론 순서와 모델 파일을 유지했다.
- 같은 세션의 계산 전체에 잠금을 적용한다. 다른 세션의 계산을 막는 전역 잠금은 두지 않았다. 잠금만으로 수신 순번이 보장되지는 않으므로 실제 스트림은 입력 순서를 유지해야 한다.
- `close()`는 계산 종료를 기다리지 않고 이력을 비운다. 계산 중 세션이 닫히면 결과 반환을 거절하고, 재접속에는 새 객체를 사용한다.

요청마다 빈 버퍼를 만들면 필요한 센서 이력이 사라진다. 회원 ID만 사용하면 같은 회원의 두 기기나
재접속을 구분하기 어렵다. 전역 잠금만 추가해도 서로 다른 측정이 한 버퍼에 들어가는 문제는 남는다.
따라서 상태의 소유 단위를 측정 세션으로 바꿨다.

## 기존 HTTP와 향후 연결

세션 식별자는 **측정 한 번에 붙이는 번호**다. 예를 들어 같은 측정의 요청에는 계속 `measurement-A`를
사용하고, 측정을 다시 시작하면 새 번호를 사용한다. 회원 인증 번호나 비밀번호가 아니다.

현재 `/predict`는 자기장·방향 6개 값만 받는다. HTTP에서 측정을 구분하려면 헤더 또는 본문에
식별자를 보내는 계약과 세션 생성·종료·만료 규칙을 정해야 한다. 구체적인 필드명과 발급 주체는 이번에 확정하지 않았다.

이번에는 앱 요청 형식을 유지하고 [HTTP 호환 모듈](../../services/legacy_prediction_service.py)에
공유 세션을 한정했다. 따라서 **추론 코어의 세션 격리는 완료했지만 기존 HTTP의 사용자 격리는 미완료**다.
향후 gRPC 스트림마다 세션 하나를 만들고 종료 시 닫도록 연결할 수 있다.
이미 코어에서 반환한 결과가 전송되기 전에 연결이 종료되는 경우도 통신 계층에서 확인해야 한다.

## 검증과 재실행

[기준 환경](../../tests/baseline/README.md)의 CPython 3.12.14 가상환경에서 실행했다.
HTTP 검증에 필요한 4개 패키지는 루트 `requirements.txt`에 이미 선언된 버전으로 설치했다.
애플리케이션 의존성이나 모델 파일은 변경하지 않았다.

```sh
.venv/bin/python -m pip install -r tests/session/requirements.txt
.venv/bin/python -m unittest discover -s tests/session -p 'test_*.py' -v
.venv/bin/python -m unittest discover -s tests/baseline -p 'test_*.py' -v
.venv/bin/python tests/baseline/prediction_baseline.py verify
```

- 세션·HTTP 호환 검증 **17개 통과**: 144개 교차 처리, 두 세션 동시 계산, 같은 세션의 계산 직렬화, 버퍼 길이 제한, 종료·재접속·늦은 결과 차단, 호환 경로와 새 세션 분리, 기존 요청·응답 유지.
- 기준 검증 **9개 통과**: 별도 프로세스 두 번에서 144개 기존 결과 일치, 결과·환경·파일 변경 감지와 기준 덮어쓰기 거절.
- HTTP는 예측 라우터만 등록한 임시 FastAPI 앱에 ASGI 메시지를 전달했다. `app.py`·업무 DB를 불러오거나 실제 네트워크 서버를 기동하지 않았다.
- 기존 `reference.json`과 합성 입력·모델 6개는 보존했다. 기준 결과의 SHA-256은 `7f381acd5fa8e260c0bbad5748ba8d070d68627e5d5e6fb011e8fbc68106333c`다.

실행 코드: [세션 검증](../../tests/session/test_prediction_session.py), [HTTP 호환 검증](../../tests/session/test_http_compatibility.py), [기준 실행 도구](../../tests/baseline/prediction_baseline.py).

## 남은 작업과 포트폴리오 표현

실제 gRPC 연결·취소·재접속 연동, 작업자·큐·연결 수 한도, 입력 검증 강화와 모델 생명주기 분리는 남아 있다.
기존 모델 버전 불일치 및 수치 연산 경고도 해결하지 않았다. Linux/EC2·실제 위치 정확도·부하 성능은 미검증이다.
이번 결과는 측정 간 이력 혼합을 막는 정확성 개선이며, 처리량이나 지연 시간이 개선됐다는 근거로 사용하지 않는다.

포트폴리오에는 다음처럼 구현 범위와 한계를 함께 설명할 수 있다.

> 공유 센서 버퍼에서 두 측정의 입력을 교차 처리할 때 단독 실행 대비 96개 중 25개의 위치 코드가 달라지는 문제를 합성 데이터로 재현했다. 추론 코어의 상태를 측정 세션 단위로 분리하고 같은 세션의 계산 직렬화와 종료 후 결과 차단을 적용했다. 기존 144개 예측 결과를 유지하면서 교차·동시 실행 및 수명 검증을 통과했다. 실제 통신 연결에 적용하는 작업과 기존 HTTP 공유 상태의 전환은 후속 과제로 구분했다.

관련 계획: 후속 설계 문서의 구현 계획. 성능 전후 비교는 추후 같은 조건의 부하 테스트에서 별도로 기록한다.
