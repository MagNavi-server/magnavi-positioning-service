# 첫 예측 시점 불일치와 Spring–Python 계약 통일

구현·검증일: 2026-10-28 (한국 시간). Python은 [PR #6](https://github.com/MagNavi-server/magnavi-positioning-service/pull/6)으로 중앙 `develop`에 반영했다. 대응 Spring 변경은 아직 로컬 미커밋이며 운영 장애·배포 사례는 아니다.

## 문제와 확인된 원인

Python은 센서가 하나 들어와도 부족한 윈도우를 채워 예측했다. 반면 Spring의 기존
`ModelProtocol.result()`는 처음 15개 응답을 `warming_up`으로 요구하고 예측은 16번째부터 허용했다.
따라서 기존 Python 결과를 그대로 연결하면 첫 예측이 규격 오류로 거절되는 코드상 불일치가 있었다.
운영에서 발생한 장애로 재현한 것은 아니며, 연결 준비 과정의 코드·설정 대조로 발견했다.

모델 전처리 파일의 윈도우 크기는 16이고 `warmup_policy`는 저장되어 있지 않다.
현재 로더가 `pad` 기본값을 적용한다. 이는 초기 입력이 부족할 때 마지막 값으로 채워 계산하는
방식이며, 16개가 쌓일 때까지 아무 결과도 보내지 않는 `wait`와 다르다.
윈도우 크기를 곧바로 대기 횟수로 해석한 계약 가정이 서로 달랐다.

위치 코드도 Python은 정수, Spring 계약은 문자열이었다. 실제 인코더 65개 라벨·29개 코드에는
정수→문자열 변환으로 표현이 바뀌는 값이 없었다. `007` 손실은 현재 모델에서 관찰한 장애가
아닌 향후 모델의 위험 예시다. 현재 정수 추론 결과를 유지하고 전송 때 문자열로 바꾼다.

## 선택과 구현

초기 15개 결과를 숨기거나 모델 전처리를 바꾸지 않고 기존 첫 샘플 예측을 유지하기로 했다.
기존 144개 회귀 결과를 보존하면서 통신 계층의 가정을 실제 동작에 맞출 수 있기 때문이다.
이 선택만으로 정확도 우열이나 지연 개선을 입증하지는 않는다.

- Spring의 `ModelProtocol`은 첫 순번부터 예측을 검증하고 v2의 워밍업 응답은 거절한다.
- 동작 계약 `contract_version=2`와 앱 경계의 `contractVersion=2`로 이전 규칙과 구분한다.
  protobuf 필드 번호·서비스 경로·패키지 v1은 유지하며 이전 동작 버전 1은 거절한다.
- Python `positioning/`은 start/ready → 센서 → 예측을 연결한다. 모델 6개 해시와 등록값을
  확인하고 RPC마다 세션을 소유한다. 입력 누락·순번·시간·유한값과 결과 후보를 검사한다.
- 통신 루프 밖의 계산 작업자·대기 수·활성 RPC·메시지 크기·대기 시간을 제한한다.
  취소된 계산이 실제 끝나기 전까지 용량을 유지해 재접속이 작업 한도를 우회하지 못하게 한다.
- FastAPI와 gRPC가 같은 모델 수명을 사용하며 DB 없이 검증할 실행 경로도 추가했다.
  기존 HTTP 응답·모델 계산·기준 결과는 유지했다.

## 실제 검증 결과

| 검증 | 결과 |
|---|---|
| Python 전체 | 76개 통과: 기준 9·세션/HTTP 22·런타임/앱 21·계약 8·실제 gRPC 16 |
| Python 실제 gRPC | 합성 3종 144개 결과, 첫 번째·15·16번째 포함 기존 코드·후보·점수 일치 |
| 측정 격리 | 두 측정의 96개 교차 입력이 각각의 단독 기준 결과와 일치 |
| 연결/계산 수명 | 취소·재접속·늦은 결과·대기 작업 취소·서버 종료·계산 용량·기한 만료 검증 |
| Spring 전체 | 269개 통과, 실패·오류·건너뜀 0, 실행 JAR 빌드 성공 |
| Spring 실제 Python 호출 | `PythonModelIntegrationTests` 1개 실행, Java 클라이언트가 기존 144개 결과 수신·비교 |
| 기존 기준 별도 비교 | `prediction_baseline.py verify` 성공; 기준 재생성 없이 비교 |
| 의존성 | 별도 `build/streaming-venv` 구성 및 `pip check` 통과 |

Spring 전체 명령은 `MAGNAVI_PYTHON_ROOT`에 Python 저장소 절대 경로를 지정한
`./gradlew test build --no-daemon`이다. Java 21과 Testcontainers의 격리 MySQL을 사용했고
운영 DB는 사용하지 않았다. 교차 언어 테스트는 DB 없이 Python 자식 프로세스를 띄우고 종료한다.
환경 변수 미지정 시 이 테스트는 건너뛰므로 일반 빌드 성공만으로 실제 모델 검증을 주장하지 않는다.

검증 과정에서 기본 실행 샌드박스의 로컬 포트 제한으로 Python 통신 테스트가 실패했다.
포트 사용이 허용된 환경에서 같은 테스트를 재실행했다. 또 앱 수명 테스트의 업무 라우터 대역에
신규 상태 경로를 연결하여 DB 접근 없이 실제 앱 구성 검증을 유지했다.

## 이력서·포트폴리오에 사용할 수 있는 설명

“Spring–Python 추론 연동 과정에서 초기 응답 규칙의 불일치를 발견하고, 기존 모델의 첫 샘플
예측을 보존하도록 계약을 버전 2로 통일했다. 스트림별 세션과 취소·자원 한도를 구현하고,
실제 Java–Python 통신에서 합성 입력 144개에 대한 기존 예측 결과의 일치를 검증했다.”

현재는 통신 호환성과 회귀 보존을 검증했다. 처리량·p95/p99·최초 결과 시간·메모리 사용량을
개선했다고 쓰려면 후속 부하 측정과 동일 조건의 변경 전후 비교가 필요하다.
기존 sklearn 저장 버전 1.5.1/실행 1.7.0 차이, 수치 경고, 실제 센서 단위·축·주파수,
운영 장소 매핑, 앱 종단 연결, Linux·TLS·배포는 남아 있다. 기존 HTTP 공유 세션도 전환 전까지 남긴다.
