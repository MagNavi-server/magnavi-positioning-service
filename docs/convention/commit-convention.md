# 커밋 컨벤션 — FastAPI/Python

작성일: 2026-09-18

적용 저장소: `MagNavi-server/magnavi-positioning-service`

관련 문서: [브랜치·PR 규칙](branch-convention.md), [프로젝트 개요](../../PROJECT_OVERVIEW.md), [구현 계획](../../IMPLEMENTATION_PLAN.md)

## 1. 이 규칙을 쓰는 이유

커밋은 변경 내용을 Git에 기록한 단위다. 제목만 읽어도 기능 추가인지, 오류 수정인지, 문서 정리인지 알아볼 수 있도록 작성한다.

두 서버는 같은 규칙을 사용하고, 작업 영역과 예시만 서버의 역할에 맞춘다. 아래 예시는 작성 방법을 보여주는 것이며 해당 기능이 구현되었다는 뜻이 아니다.

## 2. 기본 형식과 표준의 범위

[Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)을 기반으로 한다. 타입, 선택적 범위, 설명을 아래 순서로 작성한다.

```text
타입(작업 영역): 변경 내용 요약
```

이 프로젝트에서는 다음처럼 작성한다.

```text
feat(grpc): 양방향 센서 스트림 수신 추가
fix(session): 연결 종료 후 센서 버퍼 정리
docs: 프로젝트 개요 작성
```

- 타입과 작업 영역은 영문 소문자를 사용한다.
- 괄호 안 작업 영역은 선택 사항이다. 저장소 전체의 변경이면 생략해도 된다.
- 콜론 뒤에 공백 한 칸을 넣고, 요약은 한국어로 쓴다.
- 요약은 50자 이내를 권장하며, 끝에 마침표를 붙이지 않는다.
- `추가`, `수정`, `제거`, `분리`처럼 실제 변경 내용을 설명하는 표현으로 끝낸다.

형식과 `feat`·`fix`의 의미, 호환되지 않는 변경의 표시는 표준에 근거한다. 한국어 사용, 소문자 통일, 요약 길이, 작업 영역 목록은 MagNavi가 정한 세부 규칙이다. 브랜치 이름과 머지 방식은 이 표준이 아닌 별도의 프로젝트 정책이다.

## 3. 사용할 타입

기능 구현을 포함하는 커밋을 단순히 파일이 추가됐다는 이유로 `chore`로 쓰지 않는다. 반대로 빈 클래스만 배치한 작업은 완성된 기능을 뜻하는 `feat`와 구분한다.

| 타입 | MagNavi에서 사용할 기준 | 이 서버의 예시 |
|---|---|---|
| `feat` | 새로 사용할 수 있는 기능 추가 | `feat(grpc): 양방향 센서 스트림 수신 추가` |
| `fix` | 의도와 다르게 동작하는 오류 수정 | `fix(session): 연결 종료 후 센서 버퍼 정리` |
| `refactor` | 외부 동작을 유지하는 내부 구조 개선 | `refactor(inference): 모델 로딩과 추론 책임 분리` |
| `perf` | 계산·조회·메모리 사용 등 성능 개선 | `perf(inference): 샘플 처리 시 중복 변환 감소` |
| `docs` | 문서만 변경 | `docs(convention): 커밋 규칙 설명 추가` |
| `test` | 테스트 추가·수정 | `test: 잘못된 센서 입력 검증 추가` |
| `build` | 빌드 시스템·의존성 변경 | `build: 모델 실행 의존성 버전 고정` |
| `ci` | GitHub Actions 등 자동화 설정 변경 | `ci: release 브랜치 모델 서버 배포 검증 추가` |
| `chore` | 위 분류에 해당하지 않는 설정·정리 | `chore: 초기 디렉터리 골격 추가` |

모든 타입을 매번 고민해서 나눌 필요는 없다. 변경의 주된 목적을 기준으로 선택한다. 여러 독립적인 목적이 섞였다면 커밋을 나누는 것이 먼저다.

`docs` 등 추가 타입은 프로젝트가 채택한 관례다. `perf`라는 이름만 붙인다고 버전이 자동으로 올라가지는 않는다. 자동 버전 산정·변경 이력 생성 도구는 별도 구축 대상이며, 현재 이 문서가 그런 도구를 설치하거나 설정하지 않는다.

## 4. 작업 영역(scope) 선택

작업 영역은 “어느 부분을 바꿨는가”를 짧게 표시하는 이름이다. 실제 디렉터리 이름과 반드시 같을 필요는 없지만 같은 책임에는 같은 이름을 쓴다.

| 작업 영역 | 의미 |
|---|---|
| `inference` | 모델 로딩·추론 계산 |
| `preprocessing` | 자기장 보정·입력 전처리 |
| `session` | 연결별 센서 버퍼·측정 상태 |
| `grpc` | 모델 서버 통신 계약·스트림 처리 |
| `health` | 준비 상태·생존 상태 |
| `config`, `convention` | 설정, 개발 규칙 문서 |

여러 영역에 걸친 하나의 변경이면 가장 중심이 되는 영역을 선택하거나 생략한다. 새 영역이 필요하면 의미를 문서에 보완하며, 매번 다른 약어를 만들지 않는다.

## 5. 좋은 요약과 피할 요약

| 권장 | 피할 표현 | 이유 |
|---|---|---|
| `fix(session): 연결 종료 후 센서 버퍼 정리` | `fix: 오류 수정` | 어떤 오류인지 드러나야 한다 |
| `docs: 모델 연동 흐름 설명 추가` | `update` | 변경 종류와 대상을 함께 적는다 |
| `build: 실행 의존성 버전 고정` | `최종 수정 완료!!!` | 나중에 찾아볼 수 있는 기록이어야 한다 |

정말 기능을 구현했을 때만 “구현”, 실제 검증 결과가 있을 때만 “성능 개선”이라고 쓴다. 계획 문서에 기능을 설명한 것과 실제 동작을 구현한 것은 다르다.

## 6. 본문과 이슈 참조

제목만으로 충분하면 본문은 생략한다. 설계 이유나 주의점이 필요하면 제목 다음에 빈 줄을 두고 설명한다.

아래 `12`는 예시 번호다. 해당 중앙 저장소에서 실제 발급한 번호로 바꾼다.

```text
docs(convention): 커밋 및 브랜치 규칙 문서화

두 서버에서 같은 작업 절차를 사용할 수 있도록 규칙을 정리한다.
release의 CI/CD 계획과 아직 적용하지 않은 설정을 구분한다.

Refs: #12
```

- 커밋에서는 `Refs: #12`로 작업 배경을 참조한다.
- 이슈 종료 여부는 PR 본문에서 결정한다. 자세한 기준은 [브랜치·PR 규칙](branch-convention.md)을 따른다.
- 서버별 저장소는 이슈 번호가 독립적이다. 같은 숫자라도 같은 이슈가 아니다.
- 토큰, 비밀번호, 개인 연락처, 원본 센서 데이터나 상세 위치를 제목·본문에 넣지 않는다.

## 7. 호환되지 않는 변경

기존 앱이나 다른 서버가 그대로는 사용할 수 없게 되는 변경은 호환성 변경이다. 예를 들어 API 응답 필드를 제거하거나, gRPC 메시지 의미·센서 단위를 바꾸는 작업이 해당할 수 있다.

이 프로젝트는 이런 변경에 제목의 `!`와 본문의 `BREAKING CHANGE:` 설명을 함께 남긴다. 표준에서 허용하는 표시 방법에 더해, 두 서버의 전환 조건을 놓치지 않기 위한 자체 규칙이다.

```text
feat(grpc)!: 센서 메시지의 필수 순번 정보 도입

BREAKING CHANGE: 기존 송신 측의 순번 없는 메시지를 더 이상 수용하지 않는다.
양쪽 서버의 계약과 앱 전송 흐름을 확인하고 호환 기간 및 배포 순서를 정해야 한다.
```

이 예시는 형식 설명이며 실제 계약 변경 제안이 아니다. `!`를 붙이는 것만으로 안전한 전환이 되는 것은 아니다. 영향받는 서버·앱, 호환 기간, 배포 순서, 되돌릴 방법을 PR에도 적는다.

## 8. 커밋을 나누는 기준

- 하나의 커밋에는 설명할 수 있는 하나의 목적을 담는다.
- 기능과 그 기능을 검증하는 테스트는 함께 커밋해도 된다.
- 무관한 전체 포맷 변경, 문서 정리, 기능 구현을 한 커밋에 섞지 않는다.
- 작업 도중의 임시 기록은 가능하지만, 최종 PR 제목과 Squash 결과는 이 규칙으로 정리한다.
- 이미 공유한 커밋의 제목을 정리하려고 임의로 강제 push하지 않는다. 충돌·이력 수정이 필요하면 영향을 먼저 확인한다.
- 기존에 머지한 커밋은 새 규칙을 맞추기 위해 과거 이력을 다시 쓰지 않는다.

## 9. 커밋하기 전 확인

`git add .`로 모두 담기보다 필요한 파일을 명시하고, 실제 포함된 차이를 확인한다.

```bash
git status --short
git diff
git add -- docs/convention/commit-convention.md docs/convention/branch-convention.md
git diff --cached --stat
git diff --cached
git diff --cached --check
```

위 `git add`는 규칙 문서 두 개만 추가하는 예시다. 실제 변경 파일 목록에 맞춰 경로를 선택한다. `git diff`는 추적 중인 파일의 차이를 보여주므로, 새 파일은 내용을 직접 확인하고 추가 후 `git diff --cached`로 다시 살핀다.

추론 입력·출력 회귀, 세션 간 버퍼 격리, 순서·취소 처리, 모델 묶음 호환성 및 gRPC 계약 검증을 작업 범위에 맞게 선택한다. 모델 파일이나 실행 환경이 없어 일부 검증을 못 했다면 그 사실과 필요한 조건을 남긴다.

- [ ] 타입과 요약이 실제 변경 내용에 맞는다.
- [ ] 다른 작업의 파일이나 IDE 설정·임시 결과물이 섞이지 않았다.
- [ ] 민감한 값과 센서 원본·상세 위치가 포함되지 않았다.
- [ ] 실행한 검증과 실행하지 못한 검증을 구분했다.
- [ ] 이슈 번호가 이 저장소의 번호인지 확인했다.
- [ ] 호환성 변경이 있다면 전환 조건을 설명했다.

PR 제목도 같은 형식을 사용한다. 자세한 저장소·브랜치·배포 절차는 [브랜치·PR 규칙](branch-convention.md)에서 관리한다.
